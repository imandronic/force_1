Как создать первый сайт с Codex и GitHub

От небольшой задачи до проверяемого изменения: создаём HTML-страницы с Codex, знакомимся с коммитами, pull request и GitHub Pages.

В этой статье

  1. Начните с небольшой понятной задачи
  2. Разберитесь в файлах, которые появились
  3. Используйте GitHub как историю изменений
  4. Проверяйте результат до публикации
  5. Подготовьте относительные пути и GitHub Pages
  6. Используйте помощника для обучения, а не угадывания

Codex может помочь написать код, объяснить ошибку и подготовить изменение. GitHub даёт место для файлов и истории проекта. Вместе они удобны для практики, если вы ставите небольшие задачи и проверяете результат, а не принимаете каждое предложение автоматически.

Начните с небольшой понятной задачи

Первый сайт проще изучать, если его можно собрать без сложной инфраструктуры. Выберите небольшую тему: личное портфолио, страницу мастерской или учебную веб-студию. Опишите, кому предназначен сайт и что посетитель должен на нём найти. Для начала достаточно нескольких связанных страниц.

В запросе Codex перечислите конкретные требования: HTML, общий CSS, обычный JavaScript, адаптивное меню и относительные ссылки. Отдельно укажите, какие файлы нужно сохранить и что нельзя делать без согласования. Например: «Подготовь изменения для просмотра, проверь ссылки, не публикуй сайт и не объединяй PR самостоятельно».

Разберитесь в файлах, которые появились

HTML описывает содержание и структуру страницы: заголовки, абзацы, ссылки и формы. CSS отвечает за внешний вид, расположение блоков и адаптацию к разным экранам. JavaScript добавляет поведение: раскрытие меню, фильтрацию карточек или пересчёт стоимости.

Попросите Codex объяснить каждую изменённую часть простыми словами. Затем внесите небольшую правку самостоятельно: замените заголовок, цвет или подпись кнопки. Это помогает связать результат в браузере с конкретным местом в коде. Не обязательно понимать весь проект сразу, но важно постепенно разбираться, за что отвечает каждый файл и обработчик события.

Используйте GitHub как историю изменений

Репозиторий хранит файлы проекта и историю работы. Коммит фиксирует связанный набор изменений с коротким описанием. Ветка позволяет подготовить новую возможность отдельно, а pull request показывает разницу и помогает проверить её перед объединением с основной веткой.

Работайте небольшими шагами: сначала страница, затем меню, потом интерактивный блок. В PR полезно записать, что изменилось и как это проверялось. GitHub может хранить уже обновлённые файлы, пока опубликованный сайт ещё показывает старую версию: объединение изменений и успешное развёртывание — разные этапы, которые нужно проверять отдельно.

Проверяйте результат до публикации

Откройте страницы в браузере и пройдите все ссылки. Уменьшите окно до размера телефона, нажимайте Tab, попробуйте кнопки с клавиатуры. В инструментах разработчика проверьте сообщения Console и запросы Network: там можно заметить ошибку JavaScript или отсутствующий файл.

Для интерактивного блока придумайте не только обычный сценарий. У поиска проверьте пустую строку и отсутствие результатов, у калькулятора — минимальное и максимальное значения. Форму сначала можно проверить без отправки данных. Не добавляйте секреты и токены в HTML или JavaScript: эти файлы доступны посетителям сайта.

Подготовьте относительные пути и GitHub Pages

Для проекта в подпапке репозитория путь к соседней странице удобно записать как ./contact.html. Из папки articles путь к общему стилю будет ../styles.css. Начальный слеш меняет смысл адреса и может увести запрос из подпапки сайта к корню домена.

В настройках репозитория откройте Pages и выберите доступный способ публикации. Для простого статического проекта это может быть публикация из нужной ветки и корневой папки. Затем проверьте запуск в Actions: отдельно сборку и деплой. Зелёная отметка одного этапа ещё не подтверждает успешную публикацию всего сайта.

Используйте помощника для обучения, а не угадывания

Если что-то сломалось, опишите ожидаемое поведение, фактический результат и сообщение об ошибке. Попросите сначала изучить существующий код и предложить минимальное исправление. Это понятнее, чем каждый раз переписывать весь сайт, и помогает увидеть причину проблемы.

После работающего изменения обновляйте README: как посмотреть сайт, где менять тексты и как проверить новую возможность. Продолжать можно с калькулятора или собственного журнала. Выбирайте один небольшой навык за раз, проверяйте результат и сохраняйте понятную историю. Так готовый сайт постепенно становится и вашим учебным материалом.
